# Classes for Design and Debugging Transactive Mechanisms

**Author:** Trevor Hardy
**Last Update:** 13 Feb 2025

The DSO+T and Rates analysis have shown there is a need for a more systematic methodology of designing, testing, debugging, and validating a transactive mechanism. This document is an initial draft to explain how the software architecture could be designed to make these activities more easily accomplished. The core of this concept is providing coding support around defining and validating the timing and topology of the data exchanges between actors in the transactive system. With an appropriate architecture, tooling can be put in place to make development of a new transactive mechanism more easily accomplished and more clearly documented.

## UML Sequence Diagram
UML already provides a means of showing interactions between actors in a system: a sequence diagram. As of this writing, TESP has recently adopted PlantUML as a means of creating UML diagrams, primarily class and sequence diagrams. The diagrams are written in plain text and then rendereed to an image through a PlantUML server. 

A sequence diagram shows the interaction between actors in a system in terms of data exchanges between them and an order of operations. It also has standardized annotation to show activites such as loops and conditionals. For transactive systems, this is generally sufficient to show the information flow between actors in the system and when they take place.

## State Machines
To date, the transactive systems PNNL have been developing and evaluating are simple enough that they are easily described using a state machine. Generally, state machines define a series of states for a system and the logic required to move the system from one state to the next. For transactive systems, much of the activity is tied to stages in the cyclical market process and thus actors in the system have defined activities for each of the these market stages. Generally these market stages are a function of the time of day and thus, the simulation time can define the state of the system and the activity of each actor in the system (market participant) can be defined by the state.

## Data Exchanges
The operation of the system is not only dependent on the the activity of each actor as a function of the state of the system but also the information exchanges associated with the actors in a given state. Thus, to specify or understand the operation of the system, not only does the activity of each actor in the system need to be specified for each state, but also the data exchanges associated with those activities.

## Proposal: Classes to Manage State and Data Exchange
Based on our experience in TESP and the efforts in TENT (a related transactive simulation package), it seems that using something like a sequence diagram to define the operation of a transactive system is possible. Furthermore, with appropriate classes and conventions, it should be possible to create tooling that will document the implemented behavior of a system through a sequence diagram. That is, it is possible to create tooling that will take a sequence diagram written in PlantUML and define parameters for a set of standardized classes in TESP and, conversely, if a standardized set of classes in TESP have been used in implementing a transactive system, tooling could be written that would generate a PlantUML sequence diagram that reflects the implemented operation of the system, making it easier to validate said implementation.

Additionally, with standardized classes and tooling in place, data from the simulation can be collected and catergorized in such a way that it should be much easier to evaluate the simulated operation of the transactive system and inspect the actual values being exchanged. This aligns the design and the evaluation of the design much more closely, increasing confidence that the design as intended has in fact been implemented.

### State Machine Class(es)
TENT has already adopted the idea of a state machine to manage operation of the transactive system and it generally works well. For the E-COMP project, a state machine was implemented with success to manage federate operations in their market. Python already has several state machine classes and the adoption of one of these along with some customization for a transactive system should not be difficult. For example, a TESP class could be defined that defines a set of states, their transitions, and overloadable methods for each state and transition. This could then be sub-classed by all Python-based actors in the system. There would be challenges for any non-Python actors that would have to be considered. TESP has traditionally has not placed requirements on the tools it uses and the lanuages they are implmented in or have API support for.

It may make sense for there to be a state federate that is responsible for broadcasting out the state of the system based on the simulation time. There does seem to be a possibility that such a system could easily causing timing problems when used with HELICS. Alternatively, all actors in the system could be responsible for laoding in a common definition of the state machine and using it to configure their internal model. Though this would not guarantee consistency across classes in the way a central state manager would, it is likely to be just as robust, especially if the state configuration could be stored in a central database that all actors pull from.

It is unclear at the time of this writing if a single state machine for all actors is sufficient or if some actors might need sub-state machines. Or, more generally, if tying all actors to a common state machine definition is general enough to support foreseeable applications. Furthermore, the general market states defined in TENT that could be used to defined the abstract state machine class may also be too restrictive. It may be necessary to have an even more abstract class that the TENT market state machine refines and that is expected to be generally useful in TESP while allowing other, less market-oriented analysis to have a development path forward.

### Date Exchange Class(es)
At the time of this writing, the specificity of what a data exchange class is lower than that of the state machine class(es). The idea behind a data exchange class is to specify a specific data exchange (likely as a function of state and actors) that can be referenced and run (that is, the data exchange made) in a manner that is automated. For example, a data exchange can be instantiated and defined as a part of a given actor such that at the end of a given state, TESP code automatically takes the value of an attribute of the actor and sends it to the recipient of that data as defined in the data exchange class. This would allow the data exchange to be defined explicitly as part of the operation of the actor and thus is auditable and queriable by TESP tooling. Furthermore, if the analysis requires a large number of actors with the activities and data exchanges (_e.g._ the HVAC agents in the DSO+T analysis), a general class can be defined for all such actors with only the a limited number of attributes varying between the instances of that class.

The data exchange class should be general enough to handle data-exchanges via HELICS or via memory. In either case, the point in simulated time the data is exchange and the actors on both ends of the data exchange is fully defined in a standardized way.

### Design and Verification Tooling
If the above two classes are implemented in a standardized way in TESP, it will be possible to create tooling that is able to take as input a PlantUML diagram (in plain text format) that adheres to a set of conventions and from that generate the appropriate state machine and data exchange classes for a given transactive system. Conversely, it will be possible to take transactive systems implemented using these standard classes and create a PlantUML-defined sequence diagram that reflects the operation of the system in code. This strong correlation between the code used in the analysis and its documentated, graphical respresentation in a sequence diagram will make it easier for designers and programmers to clearly understand the operation of the system as designed and as implemented.

Furthermore, extensions to the data collection tooling in TESP can be made that could allow a state-aware representation of the values in the data-exchanges. For example, it could be possible for tooling in the data collection system to annotate the sequence diagram to show the values that were actually simulated. This would create a powerful debugging tool for implementers; rather than relying on time-series graphs, the data exchanges are now tied to a standardized structure and thus can have something like semantic meaning; we would be able to talk about data exchanges with respect to specific operations rather than time.

(By extension, data exchange instances could be used for general logging to capture and respresent the outputs of methods in the actor's classes. This would be similarly helpful in debugging system operation in general. )
